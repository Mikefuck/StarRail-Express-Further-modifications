# S8 结算数据读取异常的处置建议（待 Mike 确认）

此项属于 X-CUT-09 的剩余工作。Mike 对 ROLE-API-23、X-CUT-12 的“没问题”仅确认这两项 API 兼容方案，没有确认以下发奖取舍。

## 当前风险

`MatchSettlementFactory` 已在读取失败时记录原始异常，但仍可能用 `unknown`、`NONE`、部分参与者或默认阵营拼成正常 `MatchSettlement`。公开快照没有“数据不完整”标志，依赖该事件的附属模组无法可靠区分真实的无胜者结果与读取失败。

`MatchEventBridge.dispatchRoundEnded` 在构造快照之后才进入包含 `CLEANUP` 的 `try/finally`。因此，直接让快照构造失败抛出异常，还会漏掉后续角色/七宗罪的清理；必须一并处理失败路径，不能只删除 catch。

## 建议采用的规则

1. 读取局标识、最终胜负、参与者、最终胜者或结算必需阵营时发生异常，判定本次正式快照构造失败；保留异常原因和失败阶段。真正读取成功的空胜者名单继续是合法结果，不能当失败或重新推算胜者。
2. 失败时不发出 `WINNERS_FINALIZED`、公开 `MatchEvents.ROUND_ENDED` 等带正常结算含义的通知，不用空名单伪造成功快照。因此，通过这些正式结算通知自动发放的奖励不会在本次失败路径发放。
3. 正常路径继续发出相同的公开接口和最终结果。失败路径也必须执行不依赖有效快照的角色、七宗罪等跨局清理，并释放单场对局上下文。清理失败保留原始原因，避免重复执行清理或再次停局。
4. 输出明确的结算失败诊断，供管理员核对本局结果。本轮不自动推测胜者、补发奖励或重放结算；这些操作需要可信的持久记录与幂等规则。

主要修改范围：`MatchSettlementFactory` 的必要读取边界、`MatchEventBridge` 的失败/清理编排，以及 `RoleEventDispatcher`、`SevenSinEvents` 中目前依赖成功快照事件触发的内部清理注册；同时检查 `GameEndTransitionCoordinator` 对失败快照的消费。保留现有公开 API 签名。

验证会覆盖：读取故障不发布正常快照、合法空胜者仍可发布、普通失败仍执行全部必要清理、致命错误继续传播、清理恰好一次、正常结算的事件顺序与名单保持。此方案没有修改 S4 的 WinPatch 合并顺序或资产恢复规则。
